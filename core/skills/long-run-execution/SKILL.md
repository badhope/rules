# 长任务执行协议

解决的问题：任务跑得久、跨很多轮、中途被打断，导致**忘了原目标、漏了待办、重复做了已做的事**。

核心机制只有一条：**把状态从"对话历史"搬到"磁盘"**。对话会被压缩、会中断；文件不会。

## 三条铁律

1. **状态在磁盘，不在脑子里**：任何"我记得"都不算数，只认记忆文件。
2. **每次动手前先对账**：先读记忆文件的「目标」与「待办」，再决定做什么。
3. **每完成一个可交付单元就落盘**：不是等全部做完才写。

## 检查点（Checkpoint）

在以下时机**必须**更新记忆文件：

| 时机 | 写什么 |
|---|---|
| 任务开始时 | 目标、验收定义、切片计划 |
| 每完成一个切片 | 该切片"已完成 + 验证结果"；剩余待办 |
| 遇到阻塞 | 阻塞原因、已尝试方案、下一步候选 |
| 上下文可能被压缩前 | 完整当前状态快照 |
| 每次收尾前 | 对账结果（下面有清单） |

检查点格式（写进记忆文件 `## 当前状态`）：

```markdown
## 当前状态

- 更新时间：2026-10-29T08:00:00Z
- 阶段：实现中 / 验证中 / 收尾中
- 当前切片：3/7 支付模块单元测试
- 上一步结果：切片2 已通过（npm test 42 passed）
- 下一步：写切片3 的 3 个用例
- 未决问题：无 / 待用户确认 X（已按默认Y执行）
- 关键文件：src/pay.ts:120、tests/pay.test.ts
```

**为什么记「上一步结果」**：中断恢复时最大的成本不是读代码，而是搞不清"上次做到哪、结果如何"。一行结果胜过一段描述。

## 心跳（Heartbeat）

长任务进行中，每隔一段时间做一次轻量自检（写进记忆文件即可，不打扰用户）：

- 原目标还清晰吗？写一遍当前理解的目标，与文件里的目标比对。
- 待办列表还准确吗？已完成的划掉，新发现的补上。
- 有没有"做了一半"的东西？记下它在哪个文件哪一行。

**触发时机**：每完成 3 个切片、或每 30 分钟、或上下文明显变长时。

## 断点恢复（Resume）

会话重启 / 中断后，**第一件事**不是继续写代码，而是：

1. 读记忆文件的「目标」→ 确认现在要达成的还是不是它。
2. 读「当前状态」→ 上一步做到哪、结果如何。
3. 读「待办」→ 第一条未完成项是什么。
4. **验证现状**：跑一次验证命令，确认代码实际状态与记录一致（记录可能过时）。
5. 从第一条未完成项继续，不要重做已完成的部分。

第 4 步经常被跳过，但它最值钱：记录说"已完成"，代码可能被回滚了。

## 防遗忘：三重冗余

| 载体 | 内容 | 防什么 |
|---|---|---|
| 记忆文件「目标」 | 原始目标 + 验收定义 | 做着做着跑偏 |
| TodoWrite 待办列表 | 可执行的切片清单 | 漏项 |
| 记忆文件「当前状态」 | 当前位置 + 上一步结果 | 中断后不知从哪继续 |

三者不一致时，**以记忆文件的目标为准**，待办服从目标。

## 收尾对账（必做）

结束前逐项核对：

- [ ] 原始目标的每一条，都有对应的完成证据（命令输出 / 文件 / 行为）
- [ ] 待办列表全部完成，或明确标注"不做 + 原因"
- [ ] 改了的东西都跑过验证，结果真实
- [ ] 记忆文件已更新到最终状态
- [ ] 没有留下未登记的进程 / 临时文件

任一项不过，就继续做，不要收尾。

## 长任务反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 只在开头写一次计划 | 中途跑偏无人知 | 每个切片后更新时间与状态 |
| 把计划存在对话里 | 上下文压缩后丢失 | 落盘到记忆文件 |
| 中断后凭印象继续 | 重复劳动或跳过步骤 | 先读文件 + 跑验证确认现状 |
| 一口气做完再验证 | 出问题难定位是哪一步 | 一片一验证 |
| 待办只增不减 | 列表膨胀失去意义 | 完成即划掉，过时即删 |

## 与其它技能衔接

`intent-recognition`（定目标）→ `task-slicing`（拆片）→ **`long-run-execution`（跑完不丢）** → `delivery-quality-bar`（收口）。

需要跨会话交接时，用 `session-handoff` 生成冷启动文档。
