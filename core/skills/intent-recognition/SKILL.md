# 意图识别（每次开工前的第一道工序）

回答三个问题，再动手：

1. **他想要什么**（意图）：去掉手段，留下结果。
2. **这个项目是什么**（定位）：它服务的对象、解决的核心问题、所处阶段。
3. **怎么算做对了**（验收）：可观察、可执行、可复现的判据。

不识别就动手，等于替对方定义目标——这是返工的第一来源。

## 何时必须做

- 任何新任务的第一轮（非纯确认/纠正类短语）。
- 接到「优化 / 搞一下 / 看看 / 处理下」这类含糊动词。
- 跨项目、跨团队、陌生仓库接手。
- 需求方与实现方不是同一人时。

## 何时可跳过

- 用户当轮已给出完整验收标准与范围。
- 纯确认、纠正、数据粘贴（「继续」「对」「停」、日志、报错原文）。
- 已在同一任务内做过且前提未变（引用上次结论即可，不重复问）。

## 四维识别

### 1. 意图层：他到底想要什么

| 信号 | 追问方向 |
|---|---|
| 说手段不说目的（「用 Redis」） | 要解决的是缓存、锁还是队列？ |
| 说现象不说目标（「老报错」） | 报错是症状，期望的终态是什么？ |
| 说形容词不说标准（「优化一下」） | 优化哪个指标？从多少到多少？ |
| 一次提很多点 | 哪一条不做会失败？其余可延后 |

### 2. 项目定位层：这是什么项目

- **服务对象**：谁用？内部工具 / 对外产品 / 一次性脚本。
- **核心问题**：它存在是为了解决什么？删掉它谁会疼？
- **所处阶段**：原型验证 / 迭代开发 / 稳定维护 / 准备下线。
- **规模预期**：一次性 / 小团队 / 长期多人协作。
- **既有约定**：技术栈、目录结构、命名、发布方式。

阶段与规模直接决定工程强度：一次性脚本不该套分层架构，长期多人项目不能省测试。

### 3. 约束层：不能碰的红线

- 技术栈与依赖限制（不擅自引入新库）。
- 兼容性（旧数据、旧接口、旧客户端）。
- 安全与合规（鉴权、隐私、审计）。
- 不可逆操作（数据迁移、删除、发布）。
- 时间与范围（哪些明确不做）。

### 4. 验收层：怎么算做完

- **命令级**：跑哪个测试 / 哪条命令、看到什么输出。
- **行为级**：用户能做什么之前做不到的事。
- **边界级**：异常输入、空态、失败路径怎么表现。

写不出验收判据，说明意图还没识别清楚。

## 输出模板

```markdown
【意图识别】
- 真实目标：<一句话，可验收>
- 项目定位：<服务对象 / 核心问题 / 阶段 / 规模>
- 干系人：<谁关心结果，谁会被影响>
- 硬约束：<技术栈 / 兼容 / 安全 / 不可逆>
- 未知与假设：<逐条，标注为假设并给出默认值>
- 验收定义：<命令或可观察行为>
- 不做什么：<明确排除项>
```

## 规则

- **假设显式化**：缺信息按最合理默认值补全并标注「假设」，不阻塞、不反复追问。
- **不替换目标**：只提高精度，不擅自扩大或缩小范围。
- **方向分歧**：按 AGENTS.md「五方案对比 → 自选最优 → 直接执行」处理，不把选择抛回用户。
- **冲突即指出**：用户要求与项目定位矛盾时，直接说明并给替代方案。
- **可证伪**：验收定义必须能被一条命令或一次观察否证。

## 与后续步骤的衔接

意图识别 → `skill-router` 选技能 → `task-slicing` 拆片 → 开工 → 每片验证 → `delivery-quality-bar` 收口。

项目定位不明且仓库陌生时，接 `repo-cartography` 先出一页地图；规模与阶段判断影响架构强度时，接 `senior-architect`。

## 反模式

- 把用户的方案当需求（他要的是「别再卡」，不是「上 Redis」）。
- 用「我理解你要…」替代确认，然后按自己的理解做完全程。
- 识别完不写下来，做到一半忘了原始目标。
- 对小脚本套用大项目流程，或对大项目省略验收标准。

## 纠偏：用户说错了怎么办

用户经常给出**错误的实现建议**，但真实目标是对的。这时不能照做，也不能停下问他——要纠偏。

### 判定：是"目标"错了还是"路径"错了

| 信号 | 判断 | 做法 |
|---|---|---|
| 他要的结果合理，但方案明显更差/不可行 | **路径错，目标对** | 换路径，说明理由 |
| 他要的结果本身自相矛盾 | **目标需澄清** | 按最合理理解执行，标注假设 |
| 他明确说"就要这样" | **偏好，不是错误** | 照做 |
| 涉及合规/安全红线 | **不能妥协** | 指出风险，按合规方案执行 |

### 常见"路径错"类型

| 类型 | 例子 | 正确处理 |
|---|---|---|
| 技术选型错 | 小工具引入重型框架 | 用更轻方案，说明取舍 |
| 架构过度 | 一次性脚本要求分层架构 | 按规模给最小结构，说明为什么 |
| 架构不足 | 长期多人项目说"不用测试" | 补最小测试集，说明长期成本 |
| 遗漏关键步骤 | 只说"改字段"没说数据迁移 | 补迁移与回滚方案 |
| 违反工程范式 | 命名/分层明显反模式 | 按规范做，交付里指认 |
| 方案会阻碍目标 | 要求"快速上线"却选了最慢路径 | 选更快的等价方案 |

### 纠偏的三条纪律

1. **不停下问**：纠偏是自主决策，不是征询。按 AGENTS.md §五 第 18 条执行。
2. **必须说明**：交付里写清「你的原方案 / 为什么不采用 / 我改用了什么 / 为什么这样更能达成你的目标」。不能默默改掉，让他不知道。
3. **保留他的取舍权**：涉及偏好与业务判断的（不是技术错误），照他的意思做；只在"技术上明显不对"时纠偏。

### 纠偏输出模板

```markdown
【路径调整】
- 你的方案：<原话>
- 我判断的问题：<会阻碍什么目标 / 违反什么范式>
- 我采用的方案：<替代方案>
- 为什么更好：<对应到他的目标>
- 如果你仍要原方案：告诉我，我改回（当前先按更好的路径执行）
```

## 高成本任务的「假设执行窗口」

普通任务按默认值补全假设直接做即可。但**不可逆操作**或**成本超过 1 天**的任务，猜错的代价很大——需要给用户一个极低成本的纠错窗口，但**仍然不能停下等回复**。

### 触发条件（满足任一）

- 不可逆：删除数据、覆盖生产、改写 git 历史、发版上线、对外发送。
- 高成本：预计工作量 > 1 天，或涉及跨模块大规模重构。
- 高歧义：需求有 2 种以上合理解读，且不同解读的方向完全不同。

### 做法

在**第一条消息的最前面**放一段不超过 5 行的确认块，然后**立刻开始执行**：

```markdown
【执行假设 · 30 秒纠错窗口】
我按以下理解直接开始，如有偏差现在说，我立刻调整：
- 目标：<一句话>
- 范围：只改 <X>，不动 <Y>
- 关键假设：<1-2 条最可能出错的>
```

要点：

1. **不等回复**：写完就做，用户真觉得错会中断你。
2. **只列最可能错的 1-2 条假设**，不要罗列十条让人读不完。
3. **不可逆操作前仍要走可回滚路径**（备份/快照/dry-run），确认块不能替代回滚设计。
4. 与 §五 第 18 条一致：即便用户没回，纠偏决定权仍在你自己。

### 反例

- ❌ 「请问你希望用哪种方案？」— 阻塞，违反自主执行契约。
- ❌ 直接闷头做 2 天，假设全在脑子里 — 错了要返工 2 天。
- ✅ 「我按 A 理解开始（假设：兼容旧数据），如果不对现在说」+ 立刻动手。
