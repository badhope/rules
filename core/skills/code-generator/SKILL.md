# Code Generator — Automated Plan-to-Code Generator

Converts code-intent-planner's task plan into runnable code files. Two-tier architecture: **L1 script template engine** (fast, covers common patterns) + **L2 agent generation** (flexible, handles complex logic).

## Applicability Decision Table

| Situation | Use this skill? | Which tier |
|------|------------|--------|
| The plan is a Python FastAPI CRUD implementation | ✅ L1 script direct output | `code_generator.py --plan ... --format json` |
| The plan is a bug fix / test stub | ✅ L1 script emits a skeleton | Same as above (`fix`/`test` intent) |
| TypeScript/Go CRUD | ⚠️ Script L1 doesn't cover it; the agent renders by hand from the .j2 template | `references/templates/typescript_express_crud.ts.j2` |
| Custom / complex business logic | ⚠️ L2 generated by the agent (see the honesty statement) | The agent follows the "L2 generation discipline" |
| No implementation plan yet | ❌ Go to code-intent-planner first | — |
| Reviewing/debugging existing code | ❌ Out of scope | — |

## Honesty Statement (read first; this section is aligned item-by-item with the scripts' actual behavior)

- **L2 is a Mock inside the scripts.** The L2 path of `code_generator.py` (`generate_l2`) makes no LLM call at all: for the `implement` intent it always returns a FastAPI CRUD scaffold, and for other intents it returns empty. The `--no-mock` flag is just a marker; **there is no real LLM backend**. The actual "LLM generation" is performed by the agent running this skill (you) — the script's role is an L1 accelerator + structured reporter.
- **The scripts do not validate code.** The `validation` field in the returned JSON is always `"skip (mock mode)"`; checks like `py_compile`/`tsc`/`black` are run by the agent itself after files land on disk (workflow Step 4). "✓ generated" in the report only means "content was produced", **not** that it works.
- **The script does not read the .j2 files under `references/templates/`.** The script uses built-in in-memory templates (3 families); the .j2 files are reference material for the agent and tests to do Jinja2 rendering (4 of them). Do not confuse the two systems.
- **A scaffold ≠ a product.** The service layer L1 produces is an in-memory list store, with no auth and no persistence — it's a starting point, not an endpoint, and must be adapted to the project's real needs before delivery (see dark knowledge 1).

## Pre-flight Checks

```bash
# 1. The plan source is readable
test -f "$PLAN_JSON" && echo "OK plan present" || echo "NEED plan_json"
# 2. The project root is detectable (any match counts)
for f in package.json pyproject.toml go.mod Cargo.toml requirements.txt; do
  test -f "$project_root/$f" && echo "tech=$f" && break
done
# 3. The script and template library are in place
test -f scripts/code_generator.py && test -d references/templates && echo "OK skill complete"
```

- Expected: the plan exists; the project root matches at least one config file or is labeled `unknown`; the script and template library are in place.
- On failure: plan missing → STOP and return to the input checklist to request it; skill files incomplete → STOP and report the distribution is incomplete.

## L1 Real Coverage Table (3 built-in script families, mapped to code item by item)

| Intent type | Script key | Output files | Description |
|---------|--------|---------|------|
| implement + python/fastapi | `implement.python_fastapi_crud` | `src/{target}/models.py` + `service.py` + `api.py` | Pydantic v2 models + in-memory store service + FastAPI routes |
| fix (any stack; actually outputs Python) | `fix.runtime` | `src/{target}/{module}.py` | Guard-clause fix skeleton; slots must be filled with function_name/params/root_cause etc. |
| test (any stack; actually outputs Python) | `test.coverage` | `tests/test_{module}.py` | pytest test stub; slots must be filled with module_path/ClassName/method etc. |

- Match order: exact key `{intent}.{tech_stack.replace('/','_')}` → `{intent}.default` → intent fallback (fix→fix skeleton, test→test stub, implement+python*→CRUD) → no match returns `no_template`.
- TypeScript Express CRUD is rendered by the agent using `references/templates/typescript_express_crud.ts.j2` (needs Jinja2, or hand-substitute placeholders).
- The rendering mechanism is **naive placeholder substitution** (both `{{key}}` and `{key}` are replaced), not Jinja2 — do not use control-flow syntax in the templates.

## Workflow

### Step 1: Project context analysis

```bash
python3 scripts/code_generator.py --project examples/sample-codebase --format json --dry-run   # bundled sample; swap in your real scenario with --project <project_root>
```

- Action: the script calls project_analyzer to detect the tech stack and directory structure; the agent additionally reads 2-3 representative code files to confirm style (indentation/naming/import habits).
- Expected: JSON contains `tech_stack`, `files`, `context`.
- On failure: no config file → `tech_stack` is labeled `unknown` and continues; directory not readable → STOP and report permissions.

### Step 2: L1 template generation (script)

```bash
# Generate a report (markdown, no code written)
python3 scripts/code_generator.py --plan assets/sample-plan.json --project examples/sample-codebase --format markdown
# Persist code + JSON report
python3 scripts/code_generator.py --plan assets/sample-plan.json --format json   # the report goes to stdout (--output is the output directory; the example doesn't set it to avoid persisting into the skill package)
python3 scripts/project_analyzer.py --root examples/sample-codebase --json   # bundled sample project-context analysis; swap in your real scenario with --root <project_root>
```

- Expected: `status:"success"` and `files` contains 3 files (CRUD case); `no_template` → move to L2.
- On failure: the plan's slots lack `target` → template rendering degrades to `module`; fill in the plan first, then rerun.

### Step 3: L2 agent generation (when L1 doesn't cover it)

The agent generates per the following discipline, not relying on the script's mock L2:

1. Inject context: tech-stack config, 2-3 style samples, directory tree, key dependency versions;
2. Write test stubs or interface signatures first, then fill in the implementation (aligned with tdd-guide's RED→GREEN);
3. Output must pass Step 4 validation before it may be persisted and delivered;
4. Cap retries at 2; if it still fails, list it as "needs human intervention" — do not silently degrade to a scaffold.

### Step 4: Code validation (agent runs it; the script does not)

| Check | Method | Failure handling |
|--------|------|---------|
| Syntax | `python -m py_compile` / `tsc --noEmit` | Fix or regenerate |
| Formatting | `black --check` / `prettier --check` / `go fmt` | Auto-format and re-check |
| Imports | `pyflakes` / `eslint` | Fix and re-check |
| Smoke | Run `pytest --collect-only` on the generated test stub | Collection failure = the stub is unusable; go back to L2 |

- Expected: declare delivery only when all pass; any item that fails goes into the "validation failures" section of the progress report.

### Step 5: Test-stub generation (actually runnable)

The tdd-guide skill bundled in this pack has a real test_generator.py; the path is relative to the repository root:

```bash
python "core/skills/tdd-guide/scripts/test_generator.py" \
  --input src/auth/service.py \
  --framework pytest \
  > tests/test_auth_service.py
```

- On failure: tdd-guide not installed → skip and note it; do not block the main flow.

### Step 6: Progress report

The script's markdown mode auto-produces it (with the list of generated files and line counts); the agent appends two kinds of information: **validation results** (Step 4) and **items needing adaptation** (see the list in dark knowledge 1). In the report, "generated" and "validated" are two different states and must not be merged.

## Code-Generation Dark Knowledge (pitfalls from templates and real engineering)

1. **The scaffold's three IOUs**: the L1 CRUD scaffold always has three things that must be adapted — (1) `service.py` is an in-memory list store (lost on restart) and must be replaced with a real persistence layer; (2) there is no auth/permission check, so the routes in `api.py` are exposed bare; (3) there is no pagination, and `find_all` becomes an incident once data volume grows. The delivery notes must list these three, making the "IOUs" explicit.
2. **One slip in the naming-derivation chain breaks everything**: the `target` slot determines `Model = target.capitalize()`, `Service = target + "Service"`, `id_param = target minus trailing s + "_id"`. If `target` is plural (e.g. `orders`), the Model becomes `Orders` and id_param becomes `order_id` — use a singular module name first and consider table-name plurals, or override explicitly in the plan's slots.
3. **The boundary of template-first**: templates cover "shape" (layering, naming, route style), never business rules, auth, or concurrency control. To judge whether a requirement can go L1: if sub_tasks contain words like "validate inventory / risk control / notification", go straight to L2.
4. **Must validate before persisting**: a "✓ generated" in the report is only content production; something that doesn't even pass py_compile will pollute the project once persisted — the agent's validation step (Step 4) cannot be skipped; better to redo it.
5. **Style consistency comes from samples, not imagination**: before L2 generation, read 2-3 real files (indentation, quotes, import ordering, exception-handling habits); the generated code should look "written by someone on this project", not like a textbook.

## Red Lines

1. **Do not fake validation**: code that hasn't been through py_compile/tsc must not appear as "validation passed" in the report.
2. **Do not silently degrade**: after 2 failed L2 retries, list it as "needs human intervention"; do not substitute a scaffold for complex-logic delivery.
3. **Do not overwrite existing files**: when the target file exists, read and merge first (or get consent); do not overwrite directly.
4. **Do not fabricate the delivery manifest**: the "generated + pending + failed" counts in the report must correspond one-to-one with actual artifacts.
5. **Do not improvise beyond the plan**: don't implement features outside the plan on the side; put suggestions in the report.

## Failure Handling Table

| Symptom | Cause | Action |
|------|------|------|
| `no_template` | The intent type or tech stack isn't among the 3 families | Move to L2 (agent generation); or render from the .j2 template |
| Rendered code contains unreplaced placeholders | Plan slots miss keys like `target` | Fill in the plan's slots and rerun |
| L2-generated code fails to compile | Logic error/hallucination | Retry L2 (≤2 times); if it still fails, list for human intervention |
| Missing dependency | The template imports an uninstalled package | Report the missing dependency; install after consent |
| File conflict | The target file already exists | Read the existing file and merge; don't overwrite |
| `--output` points to a nonexistent deep directory | Path issue | The script auto-creates parent directories; if it still fails, use a relative path |

## Collaboration with tdd-guide

After code-generator produces code, it can automatically call tdd-guide:

```text
code-generator → generate code files → agent validation (Step 4) → tdd-guide (test_generator.py) → generate test stubs → validate stub syntax → completion report
```

**TDD-first mode** (optional): generate test stubs first (RED) → implement code to make tests pass (GREEN) → refactor (REFACTOR). Enable by including `tdd: true` in the plan.

## Delivery Criteria

- Definition of success: all generatable sub_tasks in the plan produce files, and **agent validation** (Step 4) passes or is explicitly listed as "needs human intervention".
- Artifact naming: follow the plan's target and module conventions (e.g. `src/{target}/model.py`, `tests/test_{target}_service.py`).
- Save location: code → `--output` (defaults to current directory); report → stdout unless `--format json` persists it alongside the code.
- Completeness verification: rerunning Step 4 is all ✓; the "generated + pending + failed" counts match actual artifacts; the scaffold's three IOUs are written into the delivery notes.
