# 安全审计（quick / deep 双模式）

本 skill 是安全审计的**唯一入口**，替代原来的 `security-scan`（快扫）与 `deep-security-scan`（深扫）两个技能——两者的完整原文分别归档在 `references/legacy-security-scan.md` 与 `references/legacy-deep-security-scan.md`，旧目录保留短存根用于指路。

## 模式选择

| 模式 | 适用场景 | 代价 | 停止条件 |
|---|---|---|---|
| **quick**（单遍） | PR 合入前门禁、陌生仓库第一遍摸底、发版前冒烟式检查 | 一次 passes，工具 + 人工 spot check | 分级清单出完即交付，疑点标注后升档 |
| **deep**（多轮） | 上线前/重大发版门禁、quick 发现疑点需确认可利用性、支付/权限/多租户等高风险模块、安全事件复盘 | 多轮迭代，逐攻击面收敛 | 确认漏洞与待验证疑点分离，均给出复现路径 |

先跑 quick；只有命中下节任一升档条件才切 deep，不做无依据的深扫。

## 何时升档到 deep

满足任一条即升级，并在交付里写明升档理由：

1. quick 发现**可能可利用**的疑点（注入、越权、密钥泄露），需要确认是否被中间校验挡住。
2. 改动/审计范围涉及**支付、鉴权、权限模型、多租户隔离、密钥管理**。
3. 上线前或重大发版的安全门禁，且 quick 存在 high 及以上未闭环项。
4. 安全事件后的复盘加固，需要确认影响面与是否还有其他入口。
5. 合规/客户要求提供可复现的审计证据，而非风险清单。

不升档的情形：quick 只报出配置类 low/medium、依赖补丁滞后且版本不在受影响范围、纯最佳实践建议。

## quick 模式：单遍扫描

1. **依赖体检**：列直接依赖，查已知 CVE / 弃用包 / 过期版本，区分可利用性。
2. **密钥与凭据扫描**：全局扫硬编码 API Key、密码、token、私钥、Webhook 地址（含 git 历史）。
3. **注入与危险函数**：找 SQL 拼接、命令拼接、模板注入、反序列化、动态 `eval`。
4. **鉴权与会话**：路由是否漏鉴权、越权（IDOR）、JWT 校验缺失、CORS 过宽。
5. **配置与传输**：debug 暴露、错误堆栈外泄、HTTPS 强制、安全响应头。
6. **分级输出**：按统一严重度出清单，每条给 `文件:行号` + 风险 + 修复方向。

quick 检查清单：

- [ ] 依赖扫描无未修复 critical/high CVE，或有明确豁免理由。
- [ ] 仓库里无硬编码密钥（含历史提交、`.env.example` 外的真实值）。
- [ ] 数据库查询用参数化/ORM，无字符串拼接 SQL。
- [ ] 无 `exec`/`system` 拼接用户输入；文件路径做了白名单校验。
- [ ] 敏感路由都有鉴权中间件；对象级权限在服务端校验，不只靠前端隐藏。
- [ ] 生产关闭 debug / 详细错误页；错误不返回堆栈/SQL。
- [ ] 上传文件校验类型/大小/扩展名，存储不可直接执行。
- [ ] 会话/令牌有过期、httponly、secure 标志。

## deep 模式：多轮迭代

1. **第 1 轮 · 攻击面测绘**：列全部入口（HTTP 路由、RPC、消息消费、文件上传、定时任务），标记信任边界。
2. **第 2 轮 · 污点追踪**：从每个不可信输入追到 sink（SQL/命令/文件/响应），标注中间有无校验/转义。
3. **第 3 轮 · 鉴权矩阵**：逐路由 × 逐角色列表，标出谁能调、对象级权限是否校验，找越权/IDOR。
4. **第 4 轮 · 依赖与供应链**：递归查传递依赖的已知漏洞与维护状态，核对 SCA 报告。
5. **第 5 轮 · 业务逻辑**：金额计算、状态机、并发竞态、重试幂等、配额绕过等逻辑层漏洞。
6. **收敛报告**：每个确认漏洞给「位置 → 复现路径 → 影响 → 修复方案」，区分已确认与待验证。

deep 检查清单：

- [ ] 每个外部输入都追到了 sink，污点路径上的校验点已确认有效。
- [ ] 鉴权矩阵覆盖全部路由，含对象级（IDOR）与租户隔离。
- [ ] 传递依赖漏洞递归排查过，不只看直接依赖。
- [ ] 密钥溯源到 git 历史，确认是否已泄露并需轮换。
- [ ] 业务逻辑：负数金额、状态倒挂、并发扣减、重放、配额绕过已测。
- [ ] 每个确认漏洞有最小复现步骤或 PoC 思路，不是「可能有问题」。
- [ ] 待验证项单独列出，不与已确认漏洞混为一谈。

## 统一严重度

两种模式共用同一把尺子，保证 quick 与 deep 的结论可直接对比、不会因为换了模式就降级或升级：

| 级别 | 判据 | 典型例子 |
|---|---|---|
| **Critical** | 可被远程直接利用，拿数据、拿权限或 RCE，无需前置条件 | 未授权 SQL 注入、命令注入、硬编码生产密钥、反序列化 RCE |
| **High** | 需低门槛前置（普通账号、已知参数），影响数据机密性/完整性/权限边界 | 鉴权缺失、越权访问他人数据（IDOR）、可利用的依赖 CVE、存储型 XSS |
| **Medium** | 需较高前置或影响有限，或放大其他漏洞 | 信息泄露、CORS 过宽、缺少安全响应头、弱密码策略、日志含敏感字段 |
| **Low** | 最佳实践偏差，单独不可利用 | 依赖补丁滞后、日志脱敏不全、错误提示过于具体 |

分级规则：

- 按**实际可利用性**定级，不按「代码看起来危险」定级；被有效校验挡住的降级或列为已排除。
- 依赖 CVE 必须核对**当前版本是否在受影响范围**，不在范围内的不算 high。
- 「已确认 / 待验证」是独立于严重度的置信维度：待验证项写清验证方法，不先扣上 critical 的帽子。

## 交付物

**quick 交付**：分级清单，每条一行 `级别 | 位置(文件:行号) | 风险 | 修复方向`，末尾给「未覆盖部分」与升档建议。

**deep 交付**：报告结构固定为

```
# 深度安全审计报告
## 范围与方法（扫了哪些入口、用了几轮、未覆盖部分）
## 已确认漏洞（critical/high，每条含位置/复现/影响/修复）
## 待验证疑点（有嫌疑但未证实，给出验证方法）
## 已排除项（快扫报了但确认不可利用，说明理由）
## 修复优先级与上线建议
```

两种模式都必须写清：**扫了什么、没扫什么、结论的置信度**。没跑的检查不写成已通过。

## 易错点

- **只跑工具不人工看**：工具误报不甄别就全列，淹没真问题。
- **只扫工作区不扫历史**：密钥曾提交过，删了也已泄露，必须轮换。
- **把「理论风险」当 critical**：脱离可利用性分级，门禁噪音过大。
- **越权只看登录态不看对象级**：查了「要登录」没查「能不能看别人的订单」（IDOR）。
- **依赖漏洞不看版本范围**：报了 CVE 但当前版本不在受影响范围，误报为高危。
- **快扫当深扫用**：单遍扫不出复杂数据流污点问题，发现疑点要升档而不是硬下结论。
- **把疑点当结论**：没跑通复现就报「存在 RCE」，实际被某层校验挡住；必须区分已确认与待验证。
- **只做输入输出不追中间**：找到 `db.query(raw)` 没看上面是否已有白名单校验，误报。
- **漏了非 HTTP 入口**：只测 Web 路由，忘了消息消费者、定时任务、导入接口。
- **越权只测水平不测垂直**：查了普通用户能否看别人数据，没查普通用户能否调管理员接口。
- **忽略业务逻辑**：技术上全对，但「订单金额可传负数」扫不出来，必须人工推。
- **报告不可执行**：只说「存在注入风险」，不给位置和复现路径，开发无法修。
